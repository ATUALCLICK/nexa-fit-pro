O Runtime como seam único do "mundo derivado"

Strong

src/funnel/runtime.tssrc/funnel/derive.tssrc/funnel/interpolate.tsQuizPage.tsxCheckoutPage.tsxtemplates/Result.tsxscripts/copy-qa.ts

Problema

O pipeline de resolução — deriveProfile → buildTokens → applyVariants → resolvePayload — é re-executado em 3+ call sites, cada um obrigado a conhecer os 4 passos, a ordem e a precedência de tokens. O FunnelRuntime entrega telas cruas e os callers terminam o trabalho: interface grande para behavior que devia estar atrás da seam. Result.tsx ainda importa personalization direto — caller cruzando a seam do módulo errado.

Solução

O runtime passa a expor view(screenId, answers) → tela com payload já resolvido + profile + tokens, e checkoutModel(answers) → o modelo do checkout pronto. O pipeline inteiro desce para trás da interface. Callers e QA passam a falar só com a seam.

Benefícios

Locality: o pipeline vive em um lugar — bug de resolução se corrige uma vez. Leverage: o F2 (Viva Forge) vai criar novos callers (admin, preview, estágios do gerador) e todos herdam a view pronta de graça. Testes: a interface do runtime vira a superfície de teste — copy-qa deixa de replicar o pipeline e passa a chamar view().

build-map.mjs mantém seu próprio avaliador de regras

Strong

scripts/build-map.mjssrc/funnel/rules.tsscripts/persona-qa.tsscripts/copy-qa.ts

Problema

O avaliador da DSL (15 operadores) existe duas vezes: rules.ts (engine, fonte da verdade) e uma porta em JS dentro do build-map. As duas já divergiram uma vez — ops faltando na porta geraram caminhos errados no mapa. Um adapter é seam hipotética; dois adapters divergentes é dívida com juros.

Solução

build-map vira .ts e importa evalRule — exatamente como persona-qa e copy-qa já fazem. A porta JS é deletada. Zero lógica nova: é reunificação, não refactor de design.

Benefícios

Locality: corrigir um operador corrige engine, QA e mapa de uma vez. Deletion test: deletar a porta JS faz a duplicação evaporar — a complexidade volta para onde já mora (rules.ts). Testes: o comportamento do mapa passa a ser garantido pelos mesmos testes da engine.

Antes — dois adapters, um já driftou

rules.ts
15 ops · fonte da verdade
build-map.mjs
15 ops portadas à mão ⚠ driftou

engine e QA usam a 1ª · o mapa usa a 2ª · quem garante que são iguais? ninguém

Depois — um módulo, N callers

rules.ts — evalRule / evalCond
engine ✓persona-qa ✓copy-qa ✓build-map ✓ (novo)

porta JS deletada — deletion test aprovado

3

rv() / Dyn<T> — seam hipotética do mundo pré-JSON

Worth exploring

src/quiz/engine/resolve.tsxsrc/quiz/engine/types.ts4 templates (InputMeasure, Interstitial, QuestionMulti, QuestionSingle)

Problema

No mundo pré-JSON, valores de payload podiam ser funções de answers — rv() resolvia isso. Depois do F1, JSON nunca carrega função: o payload chega aos templates sempre resolvido (string). Os templates ainda se defendem de um caso impossível — um adapter = seam hipotética, e a interface (Dyn<T>) mente sobre o que um payload pode ser.

Solução

Deletar rv(), tipar payload como dados (string), ler direto. Manter Screen.next/guard como funções — essa seam é real (o runtime compila regras para funções de propósito).

Benefícios

Deletion test: deletar rv() faz a complexidade evaporar — era pass-through puro. Interface dos templates encolhe; leitores futuros não precisam entender um mecanismo morto. Pequeno, cirúrgico, e prepara o terreno para o candidato 1.

Antes — interface inflada

payload: string | ((a) => string) + caller precisa saber chamar rv()
implementação: typeof v === 'function' ? v(a) : v — e o ramo função nunca executa

interface ≈ implementação + caso morto = raso

Depois — dados são dados

payload: string — nada a saber
template lê p.headline direto

complexidade evaporou — deletion test aprovado

4

O seed vive em dois lugares com sync manual

Worth exploring

src/funnels/pilates.jsonpublic/funnels/pilates.jsonsrc/funnel/loader.tsx

Problema

O seed existe como import estático (src/funnels) e como arquivo servido (public/funnels). Toda mudança no funil exige copiar um para o outro à mão — feito 4+ vezes nesta sessão. A invariante "os dois são iguais" não é checada por nada: um dia eles divergem e o funil servido fica velho em silêncio.

Solução

Fonte única em src/funnels/pilates.json + cópia automática no prebuild (ou o loader servir o seed do import quando ?f=pilates, eliminando o arquivo de public/). Uma linha de build, zero lógica.

Benefícios

Locality: editar o funil = editar um arquivo. Deletion test: deletar a cópia de public/ não move complexidade — ela some. Elimina a classe de bug "editei um, esqueci o outro" antes que ela vire incidente em produção.

Antes — invariante na memória do dev

src/funnels/
pilates.json
⇄?
public/funnels/
pilates.json

sync manual · nada verifica · divergência silenciosa

Depois — fonte única

src/funnels/pilates.json (fonte)
↓ prebuild copia
public/funnels/pilates.json (artefato gerado)

igualdade garantida pelo build, não pela memória

O significado de {{token}} mora em dois módulos

Worth exploring

src/quiz/engine/personalization.tssrc/funnel/interpolate.tsCheckoutPage.tsx (importa projectionDate direto)

Problema

Um conceito do domínio — "o que vale cada {{token}}" — está partido: os cálculos (IMC, projeção, datas) em quiz/engine/personalization.ts, a montagem do mapa de tokens em funnel/interpolate.ts, e os tokens derivados do ICP em funnel/derive.ts. E o CheckoutPage ignora o mapa e importa projectionDate direto — caller cruzando a seam do engine para refazer à mão o que o token já daria.

Solução

Mover personalization.ts para dentro do módulo funnel (é implementation detail dos tokens, não da engine) e garantir que todo caller consuma tokens, nunca funções de cálculo. Naturalmente absorvido pelo candidato 1 — pode ser o primeiro passo dele.

Benefícios

Locality: "onde se define um token?" passa a ter uma resposta só — crítico quando o Viva Forge precisar ensinar ao LLM quais tokens existem. Leverage: o schema de tokens documentado vira contrato de geração do F2.

Antes — conceito partido em 3 caixas

personalization
funnel/
interpolate
funnel/
derive
+ CheckoutPage pesca projectionDate por fora ↷

Depois — um módulo de tokens

funnel/tokens — cálculo + derivação + montagem
callers consomem {{tokens}}nenhum import direto

Sessão × funil sincronizada em dois lugares

Speculative

QuizPage.tsx (effect)CheckoutPage.tsx (effect)store.setFunnel

Problema

A invariante "a sessão pertence ao funil ativo" é garantida por um useEffect(setFunnel) duplicado em duas páginas. Funciona hoje; cada página nova (o /admin do F2, por exemplo) precisa lembrar de replicar — ou a sessão vaza entre funis.

Solução

Mover o efeito para o FunnelProvider: troca de funil ⇒ sessão resetada + cupom aplicado, em um único lugar, para qualquer rota presente e futura.

Benefícios

Locality pequena mas real. Speculative porque hoje só há dois callers e ambos estão certos — vale fazer junto com o candidato 1, não sozinho.

Antes — invariante replicada

QuizPage: useEffect(setFunnel)
CheckoutPage: useEffect(setFunnel)

3ª página nova = 3º lugar para esquecer

Depois — provider garante

FunnelProvider: slug mudou ⇒ setFunnel(slug, coupon)

rotas não precisam saber que a invariante existe

★ Recomendação principal: Candidato 1

Atacar primeiro "O Runtime como seam único do mundo derivado". Três razões:

  1. Timing: o F2 (Viva Forge, PRD aprovado) vai criar uma leva de callers novos — admin, preview, estágios do gerador, QA no pipeline. Hoje cada um teria que reaprender o pipeline de 4 passos; com a view() na seam, todos herdam pronto.
  2. Efeito dominó: os candidatos 3, 5 e 6 são passos naturais dentro dele — deletar rv(), reunir os tokens e mover o setFunnel ficam triviais quando o pipeline desce para trás da interface.
  3. Testabilidade: a interface do runtime vira a superfície de teste — copy-qa e persona-qa deixam de replicar internals e passam a testar o mesmo que a engine usa.

Candidato 2 é independente, menor e igualmente Strong — bom segundo passo (ou primeiro, se quiser uma vitória de 30 minutos).
